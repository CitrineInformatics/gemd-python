# Contributing

## Documentation

Documentation is built using [Sphinx](https://www.sphinx-doc.org/en/master/) with the
[autodoc](https://www.sphinx-doc.org/en/master/usage/extensions/autodoc.html#module-sphinx.ext.autodoc)
extension. Build the documentation with [uv](https://docs.astral.sh/uv/):
```shell
uv run --group docs make -C docs/ html
```

All documentation source files and configuration are in the `docs/source` directory.
Documentation for all modules is autogenerated and populated in the `reference` subdirectory.
Additional reference material, such as tutorials, should be referenced in `index.rst`.

## Testing

Changes are gated on:
 * Passing unit tests with the lowest supported versions of direct dependencies
 * 100% test coverage
 * Passing `ruff check` and `ruff format --check`, configured in [pyproject.toml](pyproject.toml)
 * Removing code whose deprecation has reached its `removed_in` version
 * A [uv.lock](uv.lock) that matches [pyproject.toml](pyproject.toml)
 * Incrementing the package version number in [gemd/\_\_version\_\_.py](gemd/__version__.py), for PRs into `main`

CI also runs the unit tests against the latest versions of all dependencies. Failures there do not block a PR.

Run the same checks locally with uv:
```shell
uv run ruff check gemd tests
uv run ruff format --check gemd tests
uv run pytest --cov=gemd --cov-report term-missing:skip-covered --cov-fail-under=100 tests/
```

To run these checks before every commit, add them to a
[git hook](https://git-scm.com/book/en/v2/Customizing-Git-Git-Hooks) such as `.git/hooks/pre-commit`,
and mark the hook executable with `chmod +x`.

## Coding Style
This project follows [PEP8](https://www.python.org/dev/peps/pep-0008/), with the following exception:
* Maximum line length is 99 characters

Additionally:
* Type hints are strongly encouraged, but not required.
* Positional arguments are strongly discouraged for methods with multiple arguments,
  especially for multiple arguments of the same type.
  Keyword-only arguments are preferred instead.
  Every positional argument should be required.

For additional (non-binding) inspiration, check out the [Google Python Style Guide](https://github.com/google/styleguide/blob/gh-pages/pyguide.md).

## Removing a capability from the public API

Replace a removed capability with a shim, so that existing code that uses it keeps importing.
Each use of the shim emits a `DeprecationWarning`, so callers can find the use and delete it.
Adding a shim takes a minor version bump, because existing code keeps importing.
Deleting the shim breaks that code and takes a major version bump.

Choose the shim by what the old code can do after the removal:
* When the class works without a field's value, keep the field as a shim that stores nothing.
* When the code behind a module or exported name is gone, keep the name importable and make each use of a removed class raise an error.

### Removing a field from a class

Keep the constructor argument and the property, and store nothing:
* Mark the getter and the setter with `@deprecated` from the `deprecation` library, so that each call warns.
* The getter returns an empty value.
* The setter discards the value, even `None`.
* The constructor warns when a caller passes the argument, even an empty list. It does not warn when the caller omits the argument.
* The constructor emits the library's `DeprecatedWarning` with `stacklevel=2`, so that Python attributes the warning to the caller's line.
* The docstring keeps the argument and states that the class discards its value.

Warn on empty values too, because any value shows that the name remains in the caller's code.
`as_dict()` serializes instance attributes. The shim does not set one, so the field stays out of `as_dict()` and the JSON.
`from_dict()` passes the field to the constructor, so old JSON that includes the field loads and warns.

```python
_ALLOWED_NAMES_DETAILS = "GEMD Python discards the value."

def __init__(self, name, *, allowed_names=None, ...):
    ...
    if allowed_names is not None:
        warn(
            DeprecatedWarning("allowed_names", "3.1.0", "4.0.0", _ALLOWED_NAMES_DETAILS),
            stacklevel=2,
        )

@property
@deprecated(deprecated_in="3.1.0", removed_in="4.0.0", details=_ALLOWED_NAMES_DETAILS)
def allowed_names(self):
    """Get an empty list."""
    return []

@allowed_names.setter
@deprecated(deprecated_in="3.1.0", removed_in="4.0.0", details=_ALLOWED_NAMES_DETAILS)
def allowed_names(self, allowed_names):
    pass
```

Add tests for these behaviors:
* The constructor, getter, setter, and JSON loading each warn.
* The constructor does not warn when the argument is omitted.
* `as_dict()` and the JSON leave out the field.

### Removing a module or exported name

Keep every name that a release exported at its old import path:
* Define the stand-in classes in one private module. Constructing a stand-in raises an error whose message names the removed feature. Reading a missing attribute from the class, such as an old method, raises the same error.
* Give each module that exported a name a `__getattr__` function. It warns and returns the stand-in.
* The warning message gives the deprecation version, the removal version, and the removed feature.
* For an unknown name, `__getattr__` raises `AttributeError` and does not warn.

Python calls a module's `__getattr__` only for names that the module does not bind.
Import the private module as a module, rather than importing its names, so that each removed name reaches `__getattr__`.
Therefore, `import gemd` does not warn, and importing a removed name does.
`stacklevel=2` attributes the warning to the importing line, so Python's default filters show it in a script.

```python
"""The old feature has been removed."""

from warnings import warn

from gemd import _removed_features

_REMOVED_NAMES = {"OldFeature", "OldFeatureResult"}


def __getattr__(name):
    if name not in _REMOVED_NAMES:
        raise AttributeError(f"module {__name__!r} has no attribute {name!r}")
    warn(
        f"{__name__}.{name} is deprecated as of 3.1.0 and will be removed in 4.0.0. "
        "The old feature has been removed.",
        DeprecationWarning,
        stacklevel=2,
    )
    return getattr(_removed_features, name)
```

Add tests for these behaviors:
* Importing each removed name from each old path emits the warning.
* Each use of a stand-in raises the error.
* Importing the package does not warn.

### Scheduling the deletion

The `removed_in` gate under [Testing](#testing) checks `@deprecated` decorators from the `deprecation` library.
It fails a PR once the package version reaches a decorator's `removed_in` version.
Mark a shim with `@deprecated` wherever a function or method can carry the decorator, so that the gate requires the deletion.
Write `deprecated_in` and `removed_in` as string literals on each decorator, because the gate reads them from the source.
The gate fails a PR when a decorator lacks either keyword.
The gate reports a direct `warn(..., DeprecationWarning)` call as a non-blocking notice.
When a shim calls `warn()` directly, as the module `__getattr__` above does, add a test that fails once `__version__` reaches the removal version.
Write the test's failure message as a list of the code to delete.

## Branching strategy

This project currently follows a [feature branch workflow](https://www.atlassian.com/git/tutorials/comparing-workflows/feature-branch-workflow):
 * Feature branches and bugfixes are branched off of `main` and then opened as PRs into `main`
 * Every PR must contain a version bump following [semantic versioning](https://semver.org/)
 * Backport branches for historical versions are created as-needed off of `main`; backports are branched off of and merged into them
 
 During periods of rapid development activity, the branching strategy may change to accommodate it, but it will be kept up to date here.

## Release process

The `main` branch **does not** continuously deploy to [pypi](https://pypi.org/project/gemd/).
Rather, releases are cut explicitly by using [GitHub's releases](https://github.com/CitrineInformatics/gemd-python/releases).
To create a release:
 * Catalog the changes in order to inform release notes
   * To do this through the GitHub interface:
     * Navigate to the [GitHub compare page](https://github.com/CitrineInformatics/gemd-python/compare)
     * Set the `base` to the most recent tag (which corresponds to the most recent release)
     * Set the `compare` to the commit you want to deploy, typically `main`
   * You can use `git diff` as well, if you prefer
 * In another tab, navigate to the [GitHub release creation page](https://github.com/CitrineInformatics/gemd-python/releases/new)
 * Set the `Target` to the commit you want to deploy, typically `main`
 * Set the `Tag version` to `v{x.y.z}` where `x.y.z` is the version in [gemd/\_\_version\_\_.py](gemd/__version__.py), e.g. `v1.2.3`
 * Set the `Release title` to "GEMD v{x.y.z} is released!"
 * Populate the release notes with a 1 or 2 sentence summary and `What's New`, `Improvements`, `Fixes`, and `Deprecated` sections, as appropriate

Publishing the release triggers GitHub Actions to deploy the package to PyPI and the documentation to GitHub Pages.
Only commits on the **main** or backports branches can be released, but it need not be the most recent commit on the branch.
The tests contained within this repository are sufficient to verify a release.
